# Транзакции, MVCC и консистентность данных

DDL - определяет допустимые состояния БД
Транзакция определяет как безопасно перейти из одного допустимого состояния в другое

Тема лекции: допустим есть LLM-сервис и билинг этого сервиса. Они работают параллельно, если упадет что-то, как правильно биллинг делать?

Все действия выполняются в цепочке внутри одной транзакции.

ACID
Atomicity - все или ничего
Consistency - после фиксации соблюдаются правила (допустимое состояние)
Isolation - Параллельное выполнение исправно
Durability - COMMIT выше сбоя

AI/ML:
Atomicity: Inference - должен сохранится целиком (есть запрос, есть результат, есть лог)
Consistency: бизнес-логика сохраняется

Решение проблемы Lost Update:
- read-modify-write (+= value)
- FOR UPDATE - указываем, какие строки блокируются явно

PostgreSQL не блокирует читателей, есть механизм MVCC (Multi-Version Concurrency Control). Каждом читателю в их транзакциях предоставляется своя версия строки.

В PostgreSQL есть разные виды блокировок: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE

Чем строже блокировка - тем больше откатов
Чем больше транзакция - тем больше откатов
MVCC - решает конфликты чтения
Audit (события) - должны идти в самой транзакции
Блокировка и ожидание ее снятие - это ок, не ошибка

Есть ошибки:
Dirty Read
Non-repeatable Read
Phantom Read
Write Skew

Deadlock - отменяем последнюю транзакцию/либо все транзакции
Профилактика - ORDER BY.

Популярные и важные ошибки:
- Длинная транзакция вокруг сетевого вызова LLM/API
- SELECT - вычисление в приложении - UPDATE без защиты от конкурентов
- Надежда, что нет параллельных запросов
- Смешивание бизнес-операции и несвязанных с них изменений
- Отсутствие retry для serialization failure / deadlock victim

pg_stat_activity - активность
pg_locks - deadlock'и
