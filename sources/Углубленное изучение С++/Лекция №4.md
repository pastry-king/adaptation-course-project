
# Многопоточность и синхронизация


libpqxx - C++ обертка над ibpq с RAII для connection/transaction/result
С помощью этой библиотеки сможем подключаться к СУБД PostgreSQL

CMake - более совершенный сборщик файлов

Взаимодействие такое:
|C++ program|---DSN---|pqxx::connection|---API---|libpq|---TCP---|PostgreSQL|

Через libpq работают все языки программирования

Data Source Name варианты: (здесь указываем как подключаемся и куда)
- key/value - строка
- URI
- C++ чистый

На лекции довольно долго подключались в С++ к СУБД. В итоге в коде С++ можно использоваться операторы DML и DDL для работы с таблицами PostgreSQL.

Connection - ресурс
Transaction - это scope работы
Result - данные ответа

Не надо прятаться за ORM?

Параметризированные запросы обязательны для входных данных.
Одна connection не должна бездумно пользоваться одновременно несколькими потоками.
Для параллельной обработки естественная модель: worker получает собственную connection или connection из pool.
При исключении RAII корректно освобождает ресурсы.
Каждый work (UPDATE, DELETE)- отдельная транзакция
DDL - пишем не сами, а шаблонам (migration)

---

Одну программу можно разбить на потоки. Это удобно, ибо программа может не столлится для ввода данных, а можно параллельло работать и что-то выполнять.

Используется библиотека thread (std::thread).

Типичные ошибки:
- Data Race - потоки одновременно работают с одним объектом (пример: неправильный счетчик)

Способ починить:
Механизм Critical section - блокировала другие потоки
Переменная mutix и lockguard - другая реализация, суть та же (вроде)
atomic - что-то еще (сложно слишком ...)

Вообще потоки нужны для:
- Responsivness (чтобы не зависал UI)
- Ускорение за счет железа (параллельно на нескольких ядрах)
- Одновременное обслуживание клиентов

В контексте AI/ML сервиса - чтобы программа могла отработать множество запросов от пользователей, т.е. отправить запросы в БД (параллельная обработка запросов)

Проверить очередь - mutex (для чего-то сложного)
Счетчики - atomic (маленькое независимое состояние)

В mutex'ах возможны deadlock'и- не надо писать ручной lock/unlock без необходимости
Condition_variable - можно не "крутить" CPU в ожидании, а просто напросто прекратить выполнение потока, начать по уведомлению
Producer - тоже, что-то можно "усыплять"
jthread - более "безопасная" реализация thread (деструктор всегда с .join())

----

Модель worker_pool: есть спящие воркеры, вызываются по необходимости (по request), отпускает mutex и выполняет работу.

processed — atomic counter.
queue — под mutex. 
stop/running — atomic или stop_token.

В PostgreSQL - буду хранить метаданные о воркерах (через Registry)
