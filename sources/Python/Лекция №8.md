# Создание ML API и сервисов

REST, FastAPI, Pydantic, async, OpenAPI, PyTorch

Цель:
- превратить ML-модель в доступный по HTTP сервис
- Определить контракт API, валидировать данные и ошибки
- Загрузить модель один раз и обеспечить воспроизводимый inference

URI - Uniform Resource Identificator

Состав стенда условного:
- Скрипт - данные и модель
- Сервис - клиент запрашивает ресурсы по HTTP
- Контракт разделяет ответственность backend и ML

Состав и принципы REST:
- Ресурсы (обращаемся по URI)
- HTTP методы (описывает действие GET, POST, PUT, DELETE)
- Запросы и ответы (данные в JSON)
- Stateless (каждый запрос имеет свой контекст)

Методы HTTP:
- GET - чтение, без изменения состояния
- POST - создание ресурса или запуск вычисления
- PUT - полная замена, PATCH - частичное изменение
- DELETE - удаление

Методы должны быть защищены от повторного вызова с теми же параметрами. Важно соблюдать идемпотентность

Статусы HTTP (менять назначение этих кодов не стоит):
- 200 - ОК
- 201 - ресурс создан
- 400 - Bad Request от клиента
- 401/403 - не аутентифицирован
- 300 - Redirect
- 404 - Ресурс отсутствует, 422 - ошибка валидации
- 500/503 - ошибка сервера, временная недоступность

Контракт ML API:
- POST /predict - вычисление прогноза
- GET /health - жив ли процесс
- GET /ready - загружена ли модель
- GET /model - версия и параметры модели
Нельзя менять форму ответ без изменения версии контракта

!!! Вопрос - где живет контракт - на веб-сервере или в приложении модели (слушает порт)
!!! + где валидация - приложение, веб-сервер, WAF


JSON участвует и в запросе и в ответе

Минимальное приложение на FastAPI:
``` python
from fastapi import FastAPI

app = FastAPI(title="ML API")
@app.get("/health")

def health():
	return {"status": "ok"}
```
Можно тестировать API через Uvicorn:
- uvicorn app.main:app --reload
- /docs - Swagger UI - просмотреть контракт
- /openapi.json - машинно-читаемый контракт

Маршрутизация внутри @app.get(), показывает логику, что обрабатывать
Аннотации используются для преобразования и валидации
Pydantic - валидация типов переменных - часть валидации бизнес-логики, ограничивает предметную область, проверка длины ввода

HTTPException - часть контракта, нужно тоже учитывать в контракте. Логи ошибки и вообще логи и error trace сервиса передавать нельзя ни в коем случае. Передаем 503 и краткое описание ошибки. <- Это важно для систем мониторинга и SIEM.

В случае проксирования - смотрим, кто авторитет (прокси или итоговый ресурс), но лучше оригинал оставлять.

Возвращать произвольный словарь нельзя т.к.:
- утечки диагностических полей
- нестабильные имена полей
- нельзя проверить контракт
- интеграция с другими системами непредсказуема

Типичные ответы для ML-сервиса:
- 422 - валидация
- 503 - модель не загружена
- 404 - неизвестная модель
- 500 - неожиданная ошибка

Состав проекта:
- app/main.py - создание приложения и lifespan
- app/schemas.py - Pydantic-контракты
- app/model.py - inference без HTTP
- tests/ - проверка контрактов и поведения

Разделение слоев:
- HTTP слой - чтения и ответ
- Сервисный слой - проверки и сценрации
- ML слой - загрузка модели и inference
Главное не смешивать torch.load и обработчик маршрута (HTTP слои и сервисный слой)

OpenAPI - как писать схемы API
FastAPI - уже сам пишет
Схема - формальный контракт между командами/для клиента

Как документировать API:
- summary, description, tags
- примеры входных данных и ожидаемых ответов
- описание кодов ошибок
- номер версии модели != версия HTTP API

Обработчики:
- синхронные - для блокирующего кода, нагрузка и число потоков ограничены
- асинхронные - неблокирующее ожидание, полезны для сетевого I/O
Типичная ошибка сложные CPU вычисления - в async, решение очереди задач
Здесь появляется вопрос конкурентности inference (когда есть несколько вопросов к одной модели, нужно учитывать потоки, память и GPU ресурсы, полезны нагрузочное тестирования для поиска ограничений реальных)

Итого жизненный цикл приложений:
- lifespan загружает модель перед приемом запросов
- модель хранится в app.state
- при остановке освобождаются ресурсы
- готовность и жизнеспособность - это разные проверки

Inference в ML сервисе без градиента (по сути отключаем обучение (очевидно))

Контроль качества ML API:
- валидный вопрос - конечный ответ
- пустой массив и NaN отклоняется
- ответ содержит версию модели
- тесты HTTP не обучают модель

Как настроить наблюдаемость сервиса:
- Логировать запросы, ошибки и задержку
- Не писать в логи секреты и полные пользовательские данные
- Использовать метрики p50, p95, ошибки и число запросов
- ML метрики качество отдельно от HTTP метрик

Как соблюдать безопасность ML API:
- Ограничение размера запроса и типов данных
- Аутентификация и права на защищенных маршрутах
- Секреты - вне исходного кода
- Не доверять pickle из непроверенных источников
- Ограничить ресурсы для тяжелого inference

Как подготовиться к эксплуатации:
- Фиксировать зависимости и конфигурацию (документирование)
- Отдельные параметры host, port, model path
- Health/readiness, корректные коды ошибок
- Запуск без --reload, тесты перед поставкой
