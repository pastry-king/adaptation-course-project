Была лекция про документные СУБД. В частности MongoBD.

> **Главная мысль:** документная СУБД полезна, когда данные и операции естественно группируются вокруг одного *агрегата*: его удобно записывать и читать целиком, а также искать по полям внутри. Для ИИ-сервиса таким агрегатом часто является **один запрос к модели с результатом**, но не вся история пользователя или все файлы датасета. Формат JSON сам по себе не делает хранилище базой данных.
## 1. Что такое документ и зачем он нужен

**Документ** — структурированная запись с идентификатором: поля, вложенные объекты и массивы. Это не PDF/DOCX и не обязательно текстовый файл. Например, результат классификации объединяет сведения о модели, входе, предсказаниях и времени обработки. **Коллекция** группирует документы; в MongoDB и CouchDB детали организации коллекций/баз отличаются.

```json

{
  "_id": "req-1001",
  "schema_version": 1,
  "created_at": "2026-11-09T10:00:00Z",
  "model": {"name": "pet-classifier", "version": "2.1"},
  "input": {"language": "ru"},
  "predictions": [
    {"label": "cat", "score": 0.97},
    {"label": "dog", "score": 0.02}
  ],
  "metrics": {"latency_ms": 18},
  "status": "completed"
}

```

Это **логическая схема**, не универсальный формат для каждой СУБД: CouchDB добавит `_rev`; MongoDB хранит BSON и может назначить иной `_id`. `request_id` может быть внешним бизнес-ключом, не равным внутреннему `_id`. В примере не сохранён `input.text`: исходный запрос может содержать персональные данные.
  
**JSON ≠ документная СУБД.** JSON задаёт синтаксис значений, но не индексы, конкурентные обновления, права, резервирование или транзакции. У JSON нет встроенного типа даты и двоичных данных; дату обычно записывают строкой ISO 8601 с часовым поясом. **BSON** в MongoDB — двоичное представление с дополнительными типами (`ObjectId`, `Date`, `Binary`, `Decimal128`); «двоичное» не означает автоматически «меньше по размеру».
## 2. Как определить границы документа

- **Вкладывать**, если части обычно читаются вместе и имеют общий жизненный цикл: `model.name` + `model.version`, небольшой массив `predictions` (top-k), метрики одного запроса. Версия модели в записи — снимок того, *какой именно моделью* получен результат.
- **Выносить отдельно**, если данные независимо изменяются, имеют много связей или неограниченно растут: карточка пользователя, реестр моделей и датасетов, миллионы событий, полные артефакты обучения. Для крупных файлов — объектное/файловое хранилище со ссылкой в метаданных. У MongoDB лимит BSON-документа **16 MiB**.
- **Дублирование** может быть осмысленным снимком (имя и версия модели на момент вызова), но копирование изменяемой карточки пользователя в каждый лог создаст проблемы согласования и удаления.
- **Схема существует и без DDL**: код приложения ожидает типы и поля. `score` то числом, то строкой ломает фильтры и агрегации. Различайте отсутствующее поле (не предоставлено) и явный `null` (пустое значение); поведение запросов зависит от СУБД. Вводите `schema_version`, валидируйте запись, планируйте миграцию при чтении или пакетно и совместимость клиентов.

**Правило проектирования:** сначала перечислите запросы, частоту изменений, размеры, требования к целостности и срок хранения; затем выбирайте границу агрегата. «Один объект — один документ» — гипотеза, а не закон.
## 3. Запросы, индексы и согласованность

Без подходящего индекса фильтр по полю может просматривать всю коллекцию. Индекс ускоряет выборку, но занимает место и удорожает запись; если совпадает почти всё, сканирование может быть выгоднее. Индекс по вложенному пути (`model.version`) позволяет искать внутри документа. Для запроса «вызовы модели X за период» полезен составной индекс с равенством по модели перед диапазоном времени; порядок полей важен. У MongoDB индексы элементов массивов называются **multikey**. Смотрите реальный план (`explain`), а не только факт создания индекса.

Операция над **одним документом** и согласованная операция над **несколькими документами** — разные задачи:

  - **MongoDB**: атомарность изменения документа; многодокументные транзакции поддерживаются в соответствующей конфигурации. Репликация в replica set сама по себе не равна транзакции; важны настройки подтверждения записи и чтения.
- **CouchDB**: оптимистическая конкуренция через `_rev` (маркер текущей ревизии). Два клиента прочитали одну версию: первый записал, запись второго со старой `_rev` получит **HTTP 409 Conflict**. Клиенту надо перечитать документ и решить, как объединять изменения. `_rev` — не полноценный журнал бизнес-версий. Репликация после работы офлайн допускает конфликты, которые требуют политики разрешения.
- **SQL-СУБД с JSON**: привычные транзакции, ключи и ограничения можно сочетать с вложенным содержимым. Требования к связям и целостности могут перевесить удобство отдельной документной СУБД.

Важно: в CouchDB `PUT` **заменяет документ целиком** — пропущенные поля исчезнут. Удаление формирует *tombstone* для репликации и не означает немедленного гарантированного стирания всех копий и резервных копий.
## 4. Что выбрать для ИИ-сервиса

| Задача / профиль                                                        | Разумный вариант     | Почему / ограничение                                                                                                  |
| ----------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Временный результат по `request_id`, сессия или кэш                     | **Key-value**        | Быстрый доступ по ключу; поиск «все результаты со `score > 0.9`» без вторичного индекса потребует просмотра значений. |
| Журнал инференса, разнородные метаданные датасетов и экспериментов      | **Документы**        | Вложенные результаты и переменные параметры удобно хранить агрегатом; поля для фильтрации нужно индексировать.        |
| Богатые фильтры и агрегации по документам, массивам и вложенным полям   | **MongoDB**          | Документные запросы, aggregation pipeline, индексы; проверить транзакционные и эксплуатационные требования.           |
| Узлы периодически работают без сети и потом синхронизируются            | **CouchDB**          | HTTP API, репликация/offline-first; конфликты разрешает прикладная логика.                                            |
| Уже есть PostgreSQL, важны JOIN, ограничения и транзакции вместе с JSON | **PostgreSQL JSONB** | JSONB, операторы `->`, `->>`, `@>`, GIN и индексы по выражениям; отдельная NoSQL-СУБД не обязательна.                 |
| SQL-платформа Oracle и обработка JSON в запросах                        | **Oracle JSON**      | `JSON_VALUE`, `JSON_TABLE`, индексация путей; детали зависят от версии.                                               |
**В одном сервисе можно сочетать модели:** кэш по ключу, документный журнал запросов, реляционные сущности «пользователь — модель — версия — эксперимент». Отсутствие JOIN не устраняет связи: их придётся реализовать вложенностью, ссылками/несколькими чтениями или средствами вроде MongoDB `$lookup`.

**Почему это особенно полезно для ИИ:** результат вызова модели включает массив предсказаний, параметры и версию модели, метрики и статус; параметры экспериментов и метаданные разных датасетов меняются от задачи к задаче. Документ позволяет сохранить контекст результата для диагностики и воспроизводимости **без искусственного разнесения каждого вложенного поля по таблицам**. Но гибкость не заменяет валидацию, индексы, управление жизненным циклом и гарантии согласованности.
## 5. Короткая практика по материалам

**MongoDB** (команды `mongosh`, если запущен `mongod`):

```javascript

use ai_demo
db.predictions.insertOne({request_id: "req-1001", model: "classifier", score: 0.97, created_at: new Date()})
db.predictions.find({score: {$gte: 0.9}}, {_id: 0, request_id: 1, score: 1})
db.predictions.createIndex({model: 1, created_at: -1})
db.predictions.find({model: "classifier"}).explain("executionStats")
db.predictions.aggregate([{$group: {_id: "$model", n: {$sum: 1}}}])

```
`find` возвращает курсор; проекция сокращает выдачу. Для вложенного поля используют путь вроде `"model.version"`, для нескольких условий на **одном элементе** массива — `$elemMatch`; `$set` меняет поле, `$inc` увеличивает число. В `explain` проверьте `keysExamined` и `docsExamined`; на двух документах выигрыш от индекса не показателен.

**CouchDB** (учебная БД `ai_demo_m7`, HTTP API; `curl` в Bash). Ниже `-u ADMIN` запрашивает пароль интерактивно; не вставляйте реальные секреты в файл или URL:

```bash

export COUCH_URL='http://127.0.0.1:5984'
curl -u ADMIN -X PUT "$COUCH_URL/ai_demo_m7"
curl -u ADMIN -X PUT -H 'Content-Type: application/json' \
  "$COUCH_URL/ai_demo_m7/req-001" \
  -d '{"model":{"name":"pet-classifier","version":"1.0"},"status":"completed","processing_ms":18}'
curl -u ADMIN "$COUCH_URL/ai_demo_m7/req-001"
curl -u ADMIN -X POST -H 'Content-Type: application/json' \
  "$COUCH_URL/ai_demo_m7/_index" \
  -d '{"index":{"fields":["status","processing_ms"]},"name":"idx_status_processing","type":"json"}'
curl -u ADMIN -X POST -H 'Content-Type: application/json' \
  "$COUCH_URL/ai_demo_m7/_find" \
  -d '{"selector":{"status":"completed","processing_ms":{"$gt":30}},"fields":["_id","status","processing_ms"],"limit":20}'

```

`PUT /db` создаёт базу (повторный вызов: 412), `PUT /db/id` создаёт документ с заданным ID, `POST /db` — с автоматически выданным ID. `GET /db/_all_docs?include_docs=true` перечисляет документы, но не заменяет поиск по полям. Для селектора по `"model.version"` нужен индекс под этот путь; план проверяют через `POST /db/_explain`. Для обновления передайте актуальную `_rev` в полном теле `PUT`, для удаления — `DELETE /db/id?rev=...`. Массовая вставка `POST /db/_bulk_docs` с повторяющимися `_id` без `_rev` даст конфликты. Веб-интерфейс — `/_utils/` (Fauxton). На общей учебной базе не меняйте `/_security` и не удаляйте базу без разрешения.

**PostgreSQL JSONB**: тот же логический результат можно хранить в `jsonb` и фильтровать по содержимому: `payload @> '{"model":{"name":"classifier"}}'`; при необходимости создать GIN-индекс. Это пример того, что «хранить документы» и «использовать отдельную документную СУБД» — разные решения.
## 6. Безопасность, измерения, проверка себя

- **Минимизация для ИИ-логов:** сохранять ID, версию модели, статус, задержку и нужные метрики; не писать полный текст запроса, паспортные данные, токены или телефоны «на всякий случай». Задать сроки хранения, маскирование, экспорт/удаление, аудит; учитывать реплики и бэкапы. Для воспроизводимости эксперимента хранить версии кода и датасета, seed, параметры, метрики и ссылки на артефакты.
- **Доступ:** разделять административные и прикладные учётные записи; API должно возвращать только разрешённые поля. Не передавать произвольный JSON-фильтр клиента прямо в запрос: проверять типы и допустимые поля, иначе возможна NoSQL-инъекция. Использовать TLS и контроль ключей.
- **Выбор подтверждать измерениями:** размер и форма документа, объём данных, селективность, доля чтений/записей, конкурентность, планы запросов, p50/p95/p99 задержки, размер индексов, резервное копирование и восстановление. «1000 запросов/с» без профиля нагрузки ничего не доказывают. Учитывать совместимость версий СУБД, ОС и ядра: в пособии описан **локальный** случай сбоя запуска MongoDB 8.0.34 на конкретной VM, а не общий вывод о продукте.
