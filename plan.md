# План: прогноз почасового потребления электроэнергии с помощью LSTM

**Основа:** тема 2 из `sources/task.md`, журнал экспериментов по `sources/experiment_design.md`, устройство модели по образцу `sources/lstm_forecaster.py`. Каждый запуск — самостоятельный эксперимент: одна LSTM с заданными параметрами и сравнение с наивными прогнозами; без ARIMA и других ML-моделей. Провести не менее трёх запусков с разными настройками.

## Данные

- [OpenML Electricity, ID 46214](https://www.openml.org/d/46214) ([исходный UCI](https://archive.ics.uci.edu/dataset/321/electricityloaddiagrams20112014)); компактный Parquet загружается напрямую с OpenML вместо большого ARFF через `fetch_openml`. Это анонимные потребители, время по Португалии; регион и тип конкретного клиента неизвестны. Не путать с классификационным набором ID 151.
- Берём одного клиента (предварительно `value_0`, после проверки качества) за **2013–2014**: около 70 080 показаний мощности каждые 15 минут (**кВт**). За каждый час считаем **потреблённую энергию, кВт·ч**: сумма четырёх показаний × 0,25 часа. Получится около 17 520 точек. На графике **X — дата и час, Y — кВт·ч за этот час**. Задача — предсказать потребление следующего часа.
- Проверить полноту дат, пропуски, нули и переходы на летнее время; описать обработку. `src/prepare_data.py` показывает ход загрузки, сохраняет исходный Parquet в `data/source/`, выбранные 15-минутные значения — в `data/raw/`, почасовой ряд — в `data/processed/`.

## Выборки и ход обучения

Разделяем **по времени**, без случайного перемешивания периодов. Это обычная схема **train → validation → test**; у нас папка теста называется `forecast` по договорённости, но это не данные из неизвестного будущего:

| Папка | Период | Для чего используется |
|---|---|---|
| `data/train/` | Январь 2013 — май 2014 | Из прошлых часов составляем скользящие окна. Прогнозируем следующий час, сравниваем с фактом и **обновляем веса**. |
| `data/validation/` | Июнь — август 2014 | После каждой эпохи считаем ошибку **без обновления весов**. Выбираем лучшую эпоху **внутри этого запуска**. |
| `data/forecast/` (test) | Сентябрь — декабрь 2014 | Сразу после обучения и validation оцениваем **эту же модель с лучшими весами**; не меняем по этим результатам её веса и настройки. |

Первое окно июня может использовать последние часы мая, а первое окно сентября — последние часы августа: это уже известное прошлое, не утечка. Проверка пошаговая, **на один час вперёд**: перед следующим прогнозом уже прошедший час становится известным; мы не предсказываем целый сезон одним запуском.

Перед подачей в сеть значения **нормализуются**: например, вычитаем среднее и делим на стандартное отклонение. Среднее и отклонение вычисляем **только по train**, а к остальным периодам применяем те же числа. Перед расчётом MAE/MSE/R² возвращаем прогнозы в исходные **кВт·ч**. Это преобразование масштаба, не отдельная модель.

## Эксперименты

- `src/lstm_core.py` — небольшой код по схеме учебного примера: окна → класс PyTorch LSTM (настраиваемые слои и нейроны) → обучение → прогноз. Dropout — задаваемая вероятность временно отключить выходные нейроны при обучении; на проверке выключен. **Early stopping:** после каждой эпохи ошибка validation; если `patience` эпох нет улучшения, остановиться и взять веса лучшей эпохи.
- Примеры трёх **независимых запусков** `(окно в часах, слои, нейроны)`: **A (24, 1, 32)**, **B (168, 1, 64)**, **C (168, 2, 64)**. Их не нужно сравнивать между собой для выбора «победителя»; каждый проходит полный цикл train → validation → forecast. При обсуждении влияния факторов учитывать, что A→B меняет сразу два параметра.
- Три наивных прогноза на тех же часах: значение **предыдущего часа**, **того же часа вчера**, **того же часа неделю назад**. В каждом запуске сравнить LSTM с ними по MAE (кВт·ч), MSE ((кВт·ч)²), R² (без единиц) на validation и forecast.

## Программа и результаты

- В `src/` всего три основных файла: `prepare_data.py`, `lstm_core.py`, `experiment.py`. Последний — окно **PyQt** с иконками и текстом, без эмодзи: параметры окна/архитектуры, dropout, learning rate, optimizer, batch size, максимум эпох, `patience`, seed, устройство; **одна кнопка запуска полного эксперимента** без зависания интерфейса и график ошибок train/validation. Зависимости — в `requirements.txt`.
- `experiments/weights/experiment_<id>.pt` — лучшие веса каждого запуска и параметры для их загрузки. `experiments/experiments.csv` — ID, статус (`running` — ещё выполняется; `completed` — прошёл train, validation и forecast; `failed` — ошибка), дата/время, гипотеза, изменяемый фактор/уровень и фиксированные условия; `model_type`, источник/версия/столбец, границы трёх периодов, все настройки, seed, device, версии ПО, время выполнения, лучшая эпоха, MAE/MSE/R² **отдельно для validation и forecast** (LSTM и трёх наивных прогнозов) **в каждой строке успешного эксперимента**.
- `experiments/graphs/<experiment_id>/` — PNG, полные числовые CSV с данными ряда/ошибок/прогнозов и `manifest.json`, который сопоставляет их с экспериментом и видимыми фрагментами графиков; `experiments/reports/experiment_<id>.html` — условия, результаты, встроенные графики Matplotlib, вывод и ограничения. Форматы заданы в `templates/`, в HTML встроены машиночитаемые данные. `README.md` — запуск, смысл данных, источники и материал для защиты на 5–7 минут. Ноутбук **не обязателен**: если преподаватель требует формат из `task.md`, согласовать приложение и HTML как альтернативу либо добавить краткий ноутбук позднее.
- Для каждого запуска проверяем: на входе сети только часы **до** предсказываемого; числа для нормализации берутся только из train; метрики считаются после возврата прогноза к шкале кВт·ч. Forecast запускается **после** завершения обучения и выбора лучшей эпохи по validation, автоматически, без дополнительного обучения. Если впоследствии выбирать лучший запуск по результатам forecast, его метрики уже нельзя считать независимой оценкой такого выбора.
