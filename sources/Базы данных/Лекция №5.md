
# Redis, Valkey, key-value системы

Первая реализация - memcached
Нужны были более быстродоступные данные и код, которые PostgreSQl не может быстро доставить
Key - индекс, Value - значение
Основные методы: get, set, del, exists. Ключи - часть API
Один ключ однозначно адресует значение

Первое изобретение - Redis: атомарные серверные операции, Time-to-Live, структуры, сетевой доступ. Но он - все еще один компонент отказа

Настройка redis - /etc/redis

Есть разные структуры в Value - разные операции над ними. Можно создавать структуры, которые имеют свою логику, лежат в Redis

Inference можно записать в Redis, если ответ и запрос уже были, то результат можно храниться в Redis. Ускоряет работу, бегаем в Redis, а не запускаем работу.

Можно также подключаться в коде. Два языка - один ключ

Нужно учитывать rate limiting, cache stampede

Есть механизмы Pub, Sub, Streams, Producer. Потоки и очереди

Есть ACL, TLS, запрет секретов в ключах, аудит доступа, частная сеть, TTL

Есть аналоги key-value хранилищ: разные условия и т.д.

Redis не нужен, если:
- малая нагрузка
- уникальные запросы
Тогда достаточно PostgreSQL + local cache, недостаточно если действительно падает rps.

Истина AI/ML-системы - в СУБД, а в кэше - только для ускорения

Порт redis - 6379

Почему не все хранить в Redis?
- PostgreSQL - результаты, аудит, модели, история. Терять нельзя!
- Valkey - TTL, cache, rate limiting, временные состояния. Кэш терять можно!

Пароль не храним в коде. Используем ACL user, TLS, ключи с TTL
Секреты, PII, чувствительные промпты в кэше - требуется отдельная оценка рисков
