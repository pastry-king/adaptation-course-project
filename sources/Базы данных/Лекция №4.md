# Индексы и оптимизация запросов

Цель: доказать измерением, что выбранный индекс помогает конкретному запросу

Один запрос SQL можно выполнять несколькими вариантами. Выбирает планировщик PostgreSQL. Наша задача дать ему хорошие варианты и проверить, что он ими пользуется.

Планировщику нужна статистика. Для этого используется ANALYZE. Это нужно для оценки rows и cost.

Индекс можно создать до статистики, но планировщик может не использовать его.

Базовый индекс - B-tree. Хорошее дерево - сбалансированное. дерево. "Справа" и "слева" количество элементов одинаково.

Все в postgreSQL хранится очень странно. В виде файлов с названиям в виде чисел.

Поднять кластер - просмотреть все файлы всех баз данных.

Максимальный размер одного файла - 8 килобайт. Если что-то больше в одной записи, то используется механизм toast.

Обычно B-tree индекса строится для Primary key. При падении селективности (эффективности индексов), применяются Bitmap индекс.

Если select возвращает 90%+ строк от таблицы, Seq scan может быть быстрее индекса.

Селективность индекса зависит от условия срабатывания. Итого: выгодно, когда возвращает <5% строк.

Как раз таки статистика говорит, какая селективность будет у запроса.

Индекс усиливается в отсортированном столбце.
Индекс может быть составным. Нужно их делать под реальные нужды.

Hash-индекс, полезен для операций равенства. Когда ищем эквивалентность.

В JSONB используется индекс GIN. GIN - показывается в каких строчках находится элемент. Есть полнотекстовый поиск. Индексируем то же выражение, которое используется в WHERE.

EXPLAIN строит и показывает предполагаемый план. Показывает cost, rows, width.

EXPLAIN ANALYZE строит план и выполняет запрос, показывает estimates, actual time, actual rows, loops.

Cost - это не миллисекунды, а внутренняя стоимость запросы, исходящая из оценок CPU, альтернативных оценок. Реальное время - actual time, execution time.

Если планировщик ожидает 10 строк, а оказалось намного больше, то проблема скорее всего в статистике (ее неактуальность).

Индекс не бесплатен. Он занимает место на диске, в ОЗУ, в CPU. INSERT изменяет индексы и таблицы. Как и UPDATE, DELETE. Индекс нужно обслуживать.

ИБ аспекты:
- не использовать SELECT *
- параметризировать запросы пользователей
- EXPLAIN ANALYZE выполняет запросы!!!
- Планы запросов раскрывают структуру таблицы, predicates и характеристики
- Чем меньше читаемых данных, тем меньше поверхность случайной утечки информации


Шесть инженерных правил:
•Индекс проектируется под запрос, а не под название столбца.
•B-tree — основной выбор для equality/range/order; GIN — для множественных элементов, JSONB и FTS.
•Составной индекс имеет порядок столбцов.
•Partial index индексирует только полезное подмножество строк.
•Наличие индекса не означает, что планировщик обязан его использовать.
•Любое «ускорили» подтверждаем одним и тем же EXPLAIN ANALYZE до и после.
